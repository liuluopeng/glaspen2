# 桌面诡异 PDF 之谜(复盘)

2026-10-04 起,桌面上不断出现 `glaspen2_2026-XXX_HH-MM-SS.pdf`,没人记得
导出过。到结案时已积累 **62 份**(10-04 以来 42 份)。本文记录排查过程、
两个真凶和可复用的经验。结论先行:

> **测试绝不能有真实副作用。** 本案里 Dart 测试和 Rust 测试各泄漏一条路,
> 每跑一次测试套件就往桌面写一份开发库整本导出的 PDF。

## 现象与内容指纹

- 文件名:`glaspen2_<年>-<年内天号>_<时>-<分>-<秒>.pdf`(pdf.rs 的
  `timestamped_name` 格式)
- 大小恒定 ~8 KB;页数 14–15;**页面尺寸混杂**(3440x1440 与 1920x1080 并存)
- 尺寸混杂是关键指纹:1920x1080 是显示器上电瞬态分辨率时期的历史页
  (见 AGENTS.md 防抖踩坑),只存在于**开发库** → 内容 = 开发库整本导出,
  而不是用户某个正常页面的导出。

顺带收获:文件名天号是 `2026-291`,而 2026-10-05 真实年内天号是 278——
这批诡异文件顺手实证了 `timestamped_name` 手算天号的**闰年累计漂移 bug**,
后来统一收口到 chrono(7244f50)。诡异文件先别删,文件名本身就是证据。

## 第一轮:Dart 测试泄漏(wire 测试)

排查 FRB 面板导出按钮路径时,发现 `frb_wire_test.dart` 的"导出/删除等
写操作"测试会经 FRB 调用**真实的** `exportPdf`。要点:

- flutter_tester 进程没有 bundle id,`db_path()` 落到开发库的稳定路径,
  于是"测试导出"= 开发库整本导出;
- 当时跑全量测试它返回了 `true`——文件已经写到桌面上了。

**修复(4ff353a)**:wire 测试在开发库存在时整组跳过写操作
(`skip:` 里检查 `~/Library/Application Support/glaspen2/glaspen2-dev.db`)。

## 第二轮:密封后仍在增加 → 用户猜想命中

密封后桌面**继续**新增:10-06 19:47:09、19:47:23、19:53:39。说明还有
第二条泄漏路。用户的猜想一针见血:"有没有可能是 CFG TEST 每次测试时
生成了一个 PDF?"

**铁证(秒级对齐)**:最新一份 `glaspen2_2026-279_19-53-39.pdf` 的 mtime
与提交 a37539c 的提交时间 **19:53:39 精确到秒一致**——那次提交是
`cargo test` 通过后立刻执行的,PDF 正是最后一轮测试写的。19:47 的两份
对应功能开发中的两轮测试。

```
grep -rn "export_all_pages\|export_infinite_paged\|export_pages_by_ids" crates/ src/
```

全部调用方里,唯一的多余项在 `#[cfg(test)]` 里:

```rust
/// Generate PDF (alias for export_all_pages)
#[test]
fn test_export_pdf() {
    export_all_pages();   // 无断言, 纯"跑一下看看"的早期冒烟
}
```

每次 `cargo test` 都把开发库整本导出到桌面。时间线全部对上:10-04 以来
的 42 份 = 这几天密集的 cargo test。

## 修复

| 提交 | 内容 |
|---|---|
| 4ff353a | wire 测试密封(dev 库存在时跳过写操作组) |
| b5f6177 | 删除无断言的 `test_export_pdf` |
| 7aebe4a | 恢复为 `#[ignore]` 手动冒烟,补上真实断言 |

手动冒烟的正确形态——平时套件完全跳过,想人工检查 PDF 渲染时:

```bash
cargo test -p glaspen-core --lib pdf -- --ignored
```

```rust
#[test]
#[ignore = "有真实副作用: 导出开发库整本 PDF 到桌面; 加 -- --ignored 手动跑"]
fn export_pdf_manual_smoke() {
    let path = export_all_pages().expect("整库导出应返回路径");
    let bytes = std::fs::read(&path).expect("PDF 文件应已落盘");
    assert!(bytes.starts_with(b"%PDF"), "应是合法 PDF 头, 实得 {path}");
}
```

修复后验证方式就是复现案发场景:跑完整测试套件,桌面 PDF 数量前后不变
(85 过 / 5 ignored / 0 新文件)。

## 经验教训

1. **测试零副作用原则**。任何没有断言、却调用"写真实文件"函数的测试,
   都是一个定时排污器。测试要碰文件系统,要么临时目录,要么 `#[ignore]`。
2. **`#[ignore]` 是手动冒烟的正确形态**:保留工具价值(人工检查渲染
   效果),消除常态污染;顺手补断言,它才第一次真正"测试"了什么。
3. **封住一条泄漏 ≠ 结案**。密封 wire 测试后 PDF 仍在增加,说明还有
   第二路。症状消失才算修复,而是不是"看起来该修的都修了"。
4. **取证三板斧**(本案定位只花了一次 grep):
   - 文件内容指纹(页数/尺寸/大小)锁定数据来源;
   - **mtime × git log 秒级对齐**锁定触发时刻(提交链紧跟测试时尤其致命);
   - grep 副作用函数的**全部**调用方,包括 `#[cfg(test)]` 和 FFI/FRB
     两条桥的每一端。
5. **诡异文件先别删**:文件名、内容、时间戳都是证据。本案文件名里的
   天号漂移还顺带实证了第二个真 bug(闰年日期手算)。
